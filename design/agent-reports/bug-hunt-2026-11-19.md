## Critical

### C1 · The argv override rewrites input and output filenames

**New.** `crates/ms-cli/src/argv_guard.rs:320` and `:413`, especially `substitute`. The generic positional classifier examines values belonging to named path options. `ms encode` provides both reproductions.

```sh
n=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
ms encode --allow-argv-secret --in seed.txt --out "$n"
ls -l -- "$n" ./-
cp seed15.txt "$n"
cp seed.txt ./-
ms encode --allow-argv-secret --in "$n" --json | jq .word_count
ms encode --allow-argv-secret --in "./$n" --json | jq .word_count
```

The first command exited 0, created `./-` and left the requested filename absent. The last two invocations name the same 15-word file. The bare name returned `12` and the entropy from `./-`. Adding `./` returned `15` and the expected entropy. A digest-like basename is a valid path. Selecting a different file silently can produce a perfectly valid backup of the wrong wallet.

**Fix and regression.** Track option arity while preprocessing argv. Pass `--in` / `--out` and their values through unchanged, including `--in=...` and `--out=...`. Admit positional secrets only in actual positional slots. Keep checks on designated secret operands. Test both paths with distinct public phrases and prepopulate `./-` so a wrong read succeeds observably. Assert exact card bytes, destination existence and absence of changes to the decoy. In a scratch build with role-aware path handling, the requested output file was present and the named 15-word input produced the expected card.

### C2 · The equals spelling hashes a different phrase

**New.** `crates/ms-cli/src/argv_guard.rs:392` and `crates/ms-cli/src/cmd/hashlock.rs:205`, `ms hashlock --hashlock-phrase=…`. The phrase rule in `design/SPEC_ms_hashlock.md:391` preserves printable ASCII bytes including spaces. These invocations each supply the six bytes of `trail `.

```sh
ms hashlock --allow-argv-secret '--hashlock-phrase=trail ' --method sha256 --json | jq -r .preimage_hex
ms hashlock --allow-argv-secret --hashlock-phrase 'trail ' --method sha256 --json | jq -r .preimage_hex
printf %s 'trail ' | ms hashlock --hashlock-phrase-stdin --method sha256 --json | jq -r .preimage_hex
```

All three exited 0. The first produced `897abbb178d59a98b5bbc2f51aa5ef612730a437bd717f8a5b344d8a747d987f`, the SHA-256 of `trail`. The controls produced `59413e908f3b72e4ce859bf153fffc8054615bc3e445f7ac5e7b2adb9b8bbe70`, independently confirmed by Python `hashlib` for the supplied six bytes. The displayed values are the preimages. A policy built from the first command's digest cannot be satisfied by re-deriving from the recorded phrase verbatim.

**Fix and regression.** Split the original option token once and carry the untouched right-hand side to the hashlock phrase channel, as the passphrase branch already does. Normalize a separate copy only for classifying the option. Pin all three public commands to the six-byte oracle and check the five-byte phrase remains distinct. Preserving the original right-hand side passed this control in the scratch build.

## Important

### I1 · The report or digest stream can overwrite a named backup at exit 0

**New.** `crates/ms-cli/src/cmd/encode.rs:269` writes the card, then `:273` emits JSON. `crates/ms-cli/src/cmd/hashlock.rs:419` and `:508` have the same two destinations on the deterministic path. The overwrite helper at `crates/ms-cli/src/out.rs:85` does not compare them.

```sh

ms verify --in backup.ms1
ms encode --in seed.txt --out backup.ms1 --json > backup.ms1
ms verify --in backup.ms1
```

The first pair exited 0/0 and left a 51-byte newline-terminated card. The second exited 0/1 and left a 168-byte JSON object in `backup.ms1`. The deterministic source still exists, but a holder who stores that file as the promised card loses the ready-to-use backup. The shell opens stdout before launching the program.

The same test needs no JSON for a hashlock. Run `printf %s trail | ms hashlock --hashlock-phrase-stdin --kind sha256 --no-engraving-card --out preimage.ms1 > preimage.ms1`. It exited 0 and left a `hash:` line. Reading the named file with `ms hashlock --kind sha256 --in preimage.ms1 --no-engraving-card` exited 1. Redirecting the digest to a different file gave a readable `ms10hash…` plate and both commands exited 0.

**Fix and regression.** Before writing a named artifact, compare its destination with each regular-file stream on which this invocation will also write. Refuse an overlap with a message naming the destinations. On Unix use open-file identity (device/inode), including hard links. Compare before application-side truncation, with equivalent handle identity where supported. Keep text `encode --out` working when stdout remains empty. Test both verbs, a hard link, and the same alias between the engraving-card stderr and `--out`. The scratch encode guard made the demonstrated collision nonzero. A shell's own pre-launch truncation cannot be undone by this check.

### I2 · Completing a valid checksum-free body returns an unreadable card

**New.** `crates/ms-codec/src/codex32/mod.rs:171`, public `Codex32String::from_unchecksummed_string`. The public constructor appends the raw residue before applying the code's target. The uppercase path also appends lowercase characters.

```rust

let card = "ms10entrsqqqqqqqqqqqqqqqqqqqqqqqqqqqqcj9sxraq34v7f";
assert!(C::from_string(card.into()).is_ok());
let built = C::from_unchecksummed_string(card[..card.len()-13].into()).unwrap();
assert_eq!(built.to_string(), card);
```

The last assertion failed. The suffix was `edy78kc80nx7c` instead of `cj9sxraq34v7f`. Reparsing the returned string failed. An uppercase input produced an uppercase body followed by the same lowercase suffix. This affects consumers of the public raw-codex32 API. The high-level `encode` path uses a different constructor and emitted the correct card.

**Fix and regression.** Apply `input_own_target()` before taking the residue, emit symbols in the body's case, and run the completed string through the checked parser. Check byte equality and reparsing on the public example in both cases and on a long-code fixture. All three passed in the scratch variant. Apply R2's parser guard alongside this change so malformed raw bodies receive structured errors. The earlier coordinator baseline report recorded a coverage gap around checksum-length selection, not this bad checksum.

### I13 · A failed replacement destroys the previous valid backup

**New for the overwrite path.** `crates/ms-cli/src/out.rs:85` delegates to `mnemonic_io_lib::write::write_private`, vendored at `vendor/mnemonic-io-lib/src/write.rs:49`. In an empty directory run `ms encode --in seed.txt --out backup --no-engraving-card` and `ms verify --in backup`. Both succeeded. Then run the following Unix probe with `ms` on PATH. The file limit affects only the child.

```python
import resource, signal, subprocess
def cap_file():
    signal.signal(signal.SIGXFSZ, signal.SIG_IGN)
    resource.setrlimit(resource.RLIMIT_FSIZE, (8, 8))
```
